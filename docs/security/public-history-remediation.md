  razão social, CNPJ, registered address, cadastral e-mail, and a legal

- Other files (`current-state.json`, `decisions.json`, `strategy.md`,
  `tasks.json`, `sources.json`, quarter plan/monitoring, `history/*`) did
  not match the CNPJ/e-mail/phone patterns in this scan, but still

  media spend figures for a real client — sensitive on their own even
  without direct PII.

This is exactly the class of data CLAUDE.md section 15 and this
hardening pass's mission both say must never be public: real client

## 3. Risk

- **Confirmed exposure window:** from the first `clients/walmaq` commit

  content is purged — the exact commit dates are available via `git log
  --format=%aI f6bd757..69cd708` but are not reproduced here to avoid
  bloating this doc; run that command locally if needed.
- **Anyone who cloned, forked, or has GitHub's CDN/cache of any commit in
  that range still has the CNPJ/e-mail/representative-name data**,
  regardless of anything done to the current branch tip or even a
  force-pushed rewrite. Rewriting history changes what *new* clones see;
  it does not retract what already left the server.
- Removing `clients/` from the current tree (done in this same hardening
  pass) stops the bleeding for new clones from this point forward, but
  is **not sufficient** — the 8 commits above remain fully reachable via
  `git log --all`, GitHub's "commits" UI, raw blob URLs, and any existing
  fork/clone.

## 4. Recommended remediation strategy

1. **Do not force-push yet.** This step is intentionally left for the
   human operator (mission constraint: no destructive history operation
   without explicit authorization).
2. **Backup first, unconditionally**, even though the canonical data
   already lives safely in the private workspace
   (`~/Documentos/Trabalho/v4-bu-workspace-private`, verified byte-identical
   during this hardening pass): also keep a full clone of the *current*
   `v4-bu-autopilot` repo (with history) before any rewrite:
   ```bash
   git clone --mirror https://github.com/kauafernandes-v4companyUB/v4-bu-autopilot.git \
     ~/Documentos/Trabalho/v4-bu-autopilot-pre-purge-mirror.git
   ```
3. **Install `git-filter-repo`** (not present in this environment; the
   community-recommended tool, actively maintained, replaces the
   deprecated `git filter-branch` / BFG for this exact job):
   ```bash
   pip install git-filter-repo   # or: brew install git-filter-repo
   ```
4. **Purge the paths**, on a *fresh clone* (filter-repo refuses to run on
   a repo that isn't freshly cloned, by design, as a safety rail):
   ```bash
   git clone https://github.com/kauafernandes-v4companyUB/v4-bu-autopilot.git \
     v4-bu-autopilot-purge-workdir
   cd v4-bu-autopilot-purge-workdir
   git filter-repo --path clients/ --invert-paths
   # private/ had nothing to purge (confirmed above), but if any doubt:
   git filter-repo --path private/ --invert-paths
   ```
   This rewrites every commit, producing new SHAs from `f6bd757` onward —
   every commit on `main` after that point gets a new hash.
5. **Verify the rewrite locally** before touching the remote:
   ```bash
   git log --all --diff-filter=A --name-only -- clients/ private/
   # must return nothing
   grep -R "03.098.041" .git 2>/dev/null  # spot-check the known CNPJ is gone from packed objects too
   ```
6. **Only then, with explicit human authorization**, push the rewritten
   history:
   ```bash
   git push --force origin main
   ```
   **Impact of this force push:**
   - Every existing local clone/fork becomes divergent from `origin/main`;
     anyone who has one will need to re-clone or hard-reset to the new
     history — a normal `git pull` will not simply work for them.
   - Any open PR based on pre-rewrite commits will need to be
     re-based or recreated.
   - GitHub's own UI history for old commits (permalinks people may have
     shared, e.g. `.../commit/f6bd757`) will start 404ing once GitHub
     garbage-collects the orphaned objects.
7. **GitHub Support step (separate from the force push):** GitHub caches
   commit data (and, for a period, blobs) independently of what refs
   point where. A force-push alone does not guarantee GitHub's caches,
   any Actions logs/artifacts that embedded file contents, or search
   indexing are purged. For data of this sensitivity (real CNPJ/PII), the
   operator should also file a request with GitHub Support to purge
   cached views of the affected commits — see
   https://docs.github.com/en/site-policy/other-site-policies/github-and-trade-controls
   (support workflow for sensitive-data removal) as the closest official
   pointer.
8. **Residual limitation, unconditionally true regardless of steps 1-7:**
   any clone/fork/mirror made *before* the purge, and not itself purged,
   still has the original data. This cannot be technically undone by
   anything the repo owner does — it can only be mitigated by (a) how
   early the purge happens relative to when the repo went public, and
   (b) direct outreach to known forks, if any exist (`git ls-remote
   --heads` against known fork URLs, or GitHub's network graph, to check).
